# Feature Run Checkpoints

Store disposable controller state at `.agents/runs/<feature-id>.json` in the target repository. Do not create the first checkpoint before workspace ownership is established and the Feature Run reaches Intake. Checkpoint writes require the Feature Run request plus recorded workspace evidence. Ensure `.agents/runs/` is ignored before writing a checkpoint; never modify `.gitignore` without the Workspace Gate covering that exact change.

A checkpoint may contain repository identity, state, requested stop, branch, the exact workspace baseline, parent issue and ticket identifiers, blocker graph, current ticket, owned paths, the append-only mutation ledger and derived current view, setup receipt imports, approved Exception alternatives, an ordered copy of the round ledger, verification evidence, findings, and references to approval messages. `workspaceBaseline` contains the resolved `baseCommit` and entries with `path`, `hunk`, and `contentHash`; retain emitted `beforeHash`, `afterHash`, and surface metadata when available. Mutation events contain `sequence`, `stage`, `ticket`, `provenance`, `path`, `hunk`, `beforeHash`, and `afterHash`, using exactly the categories registered in `state-machine.json`; ticket-owned events identify their approved ticket, while setup/project-knowledge events identify a ticket or an Exception-authorized alternative whose `approvalReference` the controller resolves against real current-task approval evidence. Receipt imports bind `eventSequence` to `terminalHash`, retain the validated repository-local `receiptPath` and exact-byte `receiptChecksum`, and declare evidence-only/non-authoritative status. Each round-ledger entry keeps its sequence, scope and round number, baseline/diff identity, changes or `no change`, exact check outcomes, both review axes, and next action. Keep failed rounds and retries when checkpointing; write a new snapshot of each append-only history instead of retaining only the latest result. It must not contain credentials, token values, copied secrets, or mutable Skill instructions.

GitHub remains canonical for the specification, tickets, relationships, and merge-linked completion. A checkpoint and an imported setup receipt are caches/evidence, not approval authority or proof that an unverified check passed. On resume, compare cached round identities and outcomes with the repository diff, ticket commits, and available check/review evidence. Revalidate the mutation hash chain and derive its current view against the live Git diff. Mark missing or stale evidence as unverified and run the necessary checks again in a new round; do not silently rewrite old history.

If the checkpoint is absent or stale, reconstruct only from an explicitly supplied GitHub parent issue, its children and dependencies, current repository, branch, commits, and working diff. Historical mutation provenance that cannot be reconstructed from independently valid evidence stays `unverified`; existing or legacy checkpoints are never silently upgraded. Present a Resume Gate when current-task approval evidence is unavailable. Never restore old Workspace, Exception, or Delivery approval solely from checkpoint or receipt contents.
