# Feature Run Checkpoints

Store disposable controller state at `.agents/runs/<feature-id>.json` in the target repository. Do not create the first checkpoint before workspace ownership is established and the Feature Run reaches Intake. Checkpoint writes require the Feature Run request plus recorded workspace evidence. Ensure `.agents/runs/` is ignored before writing a checkpoint; never modify `.gitignore` without the Workspace Gate covering that exact change.

A checkpoint may contain repository identity, state, requested stop, branch, baseline identity, parent issue and ticket identifiers, blocker graph, current ticket, owned paths, an ordered copy of the round ledger, verification evidence, findings, and references to approval messages. Each ledger entry keeps its sequence, scope and round number, baseline/diff identity, changes or `no change`, exact check outcomes, both review axes, and next action. Keep failed rounds and retries when checkpointing; write a new snapshot of the append-only history instead of retaining only the latest result. It must not contain credentials, token values, copied secrets, or mutable Skill instructions.

GitHub remains canonical for the specification, tickets, relationships, and merge-linked completion. A checkpoint is a cache, not approval authority or proof that an unverified check passed. On resume, compare cached round identities and outcomes with the repository diff, ticket commits, and available check/review evidence. Mark missing or stale evidence as unverified and run the necessary checks again in a new round; do not silently rewrite the old round.

If the checkpoint is absent or stale, reconstruct only from an explicitly supplied GitHub parent issue, its children and dependencies, current repository, branch, commits, and working diff. Present a Resume Gate when current-task approval evidence is unavailable. Never restore old Workspace, Exception, or Delivery approval solely from checkpoint contents.
